# Code Review

## BACKEND

**Файл:** `TimesheetReportHandler.cs`

### 1. Неверно выбирается ставка сотрудника

**Приоритет:** 🔴 0

**Фрагмент:**

```csharp
var rate = employee.Rates.FirstOrDefault().Value;
```

**Проблема:** берётся первая ставка без учёта даты записи.

**Риск:** отчёт показывает правдоподобные, но неверные суммы после изменения ставок.

**Исправление:** выбирать последнюю ставку, для которой `From <= entry.Date`; отсутствие подходящей ставки обрабатывать явно.

---

### 2. Вся коллекция `time_entries` загружается в память

**Приоритет:** 🔴 0

**Фрагмент:**

```csharp
.Find(FilterDefinition<TimeEntry>.Empty)
.ToListAsync();

var monthEntries = entries
    .Where(e => e.Date.Year == request.Year && e.Date.Month == request.Month)
    .ToList();
```

**Проблема:** фильтрация месяца выполняется после загрузки всех записей из MongoDB.

**Риск:** расход памяти, сетевой трафик и время выполнения растут вместе со всей историей табеля.

**Исправление:** минимум — фильтровать диапазон дат в MongoDB. Для отчёта предпочтительна MongoDB aggregation с возвратом только итоговых строк.

---

### 3. N+1 запросов при построении отчёта

**Приоритет:** 🟠 1

**Фрагменты:**

```csharp
.Find(e => e.Id == entry.EmployeeId)
.FirstOrDefaultAsync().Result;
```

```csharp
.Find(p => p.Id == entry.ProjectId)
.FirstOrDefaultAsync();
```

**Проблема:** сотрудник запрашивается для каждой записи, проекты — по мере обхода записей.

**Риск:** число обращений к MongoDB растёт вместе с количеством записей месяца.

**Исправление:** MongoDB aggregation.

---

### 4. Синхронное ожидание внутри `async`-обработчика

**Приоритет:** 🟠 1

**Фрагмент:**

```csharp
.FirstOrDefaultAsync().Result;
```

**Проблема:** `.Result` блокирует поток внутри асинхронного метода.

**Риск:** ухудшение масштабируемости и поведения приложения под нагрузкой.

**Исправление:** использовать `await` и передавать `CancellationToken`.

---

### 5. Для денег используется `double`

**Приоритет:** 🟠 1

**Проблема:** `Rate.Value`, `Amount` и `Budget` представлены `double`.

**Риск:** ошибки точности floating-point в финансовых расчётах.

**Исправление:** использовать `decimal` для ставок, бюджета и денежных сумм.

---

### 6. Не обрабатывается отсутствие сотрудника или проекта

**Приоритет:** 🟠 1

**Фрагменты:**

```csharp
employee.Rates.FirstOrDefault().Value
```

```csharp
ProjectId = project.Id
```

**Проблема:** код предполагает, что связанные сущности всегда существуют.

**Риск:** `NullReferenceException` и HTTP 500 вместо диагностируемой ошибки.

**Исправление:** явно проверять результаты запросов связанных сущностей.

---

### 7. `CancellationToken` не передаётся в MongoDB

**Приоритет:** 🟡 2

**Проблема:** `token` принимается обработчиком, но запросы MongoDB его не используют.

**Риск:** работа с БД может продолжаться после отмены HTTP-запроса.

**Исправление:** передавать `token` в асинхронные операции драйвера.

---

### 8. Не обработан нулевой бюджет

**Приоритет:** 🟡 2

**Фрагмент:**

```csharp
row.Amount / row.Budget * 100
```

**Проблема:** отсутствует явно определённое поведение при `Budget == 0`.

**Риск:** некорректный процент и признаки перерасхода.

**Исправление:** валидировать бюджет либо явно определить бизнес-правило для нулевого бюджета.

---

### 9. Не валидируются `Year` и `Month`

**Приоритет:** 🟡 2

**Проблема:** обработчик принимает любые значения параметров запроса.

**Исправление:** валидировать месяц `1..12` и допустимый год до выполнения запроса.

## FRONTEND

**Файл:** `TimeEntriesPage.tsx`

### 1. Загрузка табеля запускается после каждого render

**Приоритет:** 🔴 0

**Фрагмент:**

```tsx
useEffect(() => {
  load()
})
```

**Проблема:** отсутствует массив зависимостей; `load()` меняет state и вызывает следующий render.

**Риск:** повторяющиеся запросы к API.

**Исправление:**

```tsx
useEffect(() => {
  void load()
}, [props.year, props.month])
```

---

### 2. После добавления в state попадает объект неправильной формы

**Приоритет:** 🔴 0

**Фрагмент:**

```tsx
entries.push(body)
setEntries(entries)
```

При этом таблица ожидает:

```tsx
entry.employeeName
entry.projectName
entry.amount.toFixed(2)
entry.id
```

**Проблема:** `body` не содержит этих полей.

**Риск:** после успешного сохранения следующий render может упасть, например на `entry.amount.toFixed(2)`.

**Исправление:** использовать объект, возвращённый API, либо повторно загрузить список после сохранения.

---

### 3. HTTP-ошибки считаются успешными операциями

**Приоритет:** 🟠 1

**Фрагмент:**

```tsx
await fetch(...);
alert("Сохранено");
```

**Проблема:** `response.ok` не проверяется. `fetch` не выбрасывает исключение только из-за HTTP 400/409/500.

**Риск:** пользователь может увидеть «Сохранено» после отказа сервера.

**Исправление:** централизованно проверять HTTP status и показывать текст серверной ошибки пользователю.

---

### 4. React state мутируется напрямую

**Приоритет:** 🟠 1

**Фрагмент:**

```tsx
entries.push(body)
setEntries(entries)
```

**Проблема:** нельзя мутировать state напрямую!

**Исправление:** использовать `setEntries(current => [...current, item])`.

---

### 5. Формат даты зависит от locale браузера

**Приоритет:** 🟠 1

**Фрагмент:**

```tsx
date: new Date(date).toLocaleDateString(),
```

**Проблема:** результат может быть `05.03.2026`, `3/5/2026` и т. п.

**Риск:** неоднозначный API-контракт и ошибки интерпретации даты.

**Исправление:** передавать календарную дату в стабильном формате, например `YYYY-MM-DD`.

---

### 6. `any` отключает полезную проверку TypeScript

**Приоритет:** 🟠 1

**Фрагмент:**

```tsx
const [entries, setEntries] = useState<any[]>([])
const [employees, setEmployees] = useState<any[]>([])
```

**Проблема:** TypeScript не обнаруживает несовпадение формы `body` с моделью строки таблицы.

**Риск:** ошибки API-контракта обнаруживаются только во время выполнения.

**Исправление:** определить типы `TimeEntryRow`, `Employee` и request DTO.

---

### 7. Часы хранятся и отправляются строкой

**Приоритет:** 🟡 2

**Фрагмент:**

```tsx
const [hours, setHours] = useState('')
```

**Проблема:** числовое значение передаётся как необработанная строка без клиентской валидации.

---

### 8. Ошибка запроса может оставить UI в состоянии загрузки

**Приоритет:** 🟡 2

**Фрагмент:**


**Проблема:** нет `try/catch/finally`.

**Риск:** при сетевой ошибке `loading` не сбросится, пользователь не получит понятного сообщения.

**Исправление:** обрабатывать ошибки и сбрасывать loading в `finally` либо использовать библиотеку управления server state.

**Приоритет:** 🟡 3

**Фрагмент:**


## Структурные изменения

### Backend

`TimesheetReportHandler` одновременно выполняет доступ к БД, выбор ставки, загрузку проектов, денежные расчёты, группировку и формирование ответа.

Основное изменение — перенести расчёт отчёта на сторону MongoDB и оставить handler/service координатором запроса. Правило выбора действующей ставки должно иметь единую реализацию, поскольку оно используется не только в отчёте.

### Frontend

`TimeEntriesPage` одновременно отвечает за API-запросы, server state, фильтры, форму, mutations, расчёт итогов и отображение.

Достаточно:

- определить типизированные API-контракты и единообразную обработку ошибок;
- вынести форму и таблицу в отдельные компоненты;
- отделить загрузку/mutations server state от presentation-кода;
- оставить небольшое UI-состояние локальным, пока оно не требуется нескольким экранам.

Глобальный store для этого экрана сам по себе не нужен.
